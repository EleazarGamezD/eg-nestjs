# EG AsyncAPI For WebSockets

## Apply And Preserve

Use this guide when creating, changing, or documenting WebSocket/Socket.IO gateways, or when the user asks to replicate EG AsyncAPI. Preserve existing AsyncAPI documentation, decorators, payloads, servers, security, UI route, and Swagger links. DDD/hexagonal refactors do not authorize removing them: they belong to the WebSocket adapter and its DTOs. Do not introduce WebSockets just to add documentation.

## Central Setup

The [original setup template](../assets/asyncapi/asyncapi.ts) comes from `src/core/config/asyncapi/config/asyncapi.ts` in the EG backend. It uses `nestjs-asyncapi` (the inspected project declares `^1.4.0`) with `AsyncApiDocumentBuilder` and `AsyncApiModule`.

Keep this format:

- Export an async `setupAsyncApi(app: INestApplication)` function from `core/config/asyncapi/config/asyncapi.ts`.
- Define title, channel/functionality description, version, contact, and `application/json` as the default content type.
- Define `BearerAuth` HTTP bearer JWT security, adjusted to the target backend's real authentication.
- Define local and remote environment servers with `ws`/`wss` protocols, URLs, and descriptions.
- Call `await AsyncApiModule.createDocument(app, options)` and `await AsyncApiModule.setup('sockets-docs', app, document)`.
- In bootstrap, import and execute `await setupAsyncApi(app)` before `listen`, preserving Socket.IO adapter registration. Do not replace `main.ts` with a minimal template.
- Keep `/sockets-docs` and link it from the Swagger Markdown description and `setExternalDoc`, as described in [swagger.md](swagger.md).

The template preserves original identity and URLs as a reference. In another backend, adapt title, contact, version, and servers to the real configuration. Do not copy Mercado Meet domains or introduce the private library. Reuse the installed `nestjs-asyncapi` version and APIs; if the version changes, verify compatibility before porting examples.

## Gateway Convention

The project documents direction from the backend point of view:

- `@AsyncApiSub`: incoming client-to-server events, together with `@SubscribeMessage`.
- `@AsyncApiPub`: outgoing server-to-client events, together with emission helpers that call `client.emit` or emit to a room.
- `channel`: the same enum member used by the handler/emitter; do not duplicate event names as hardcoded strings.
- `summary`: short and in English. `description`: explain flow, audience, conditions, reconnection, and variants when relevant.
- `message: { payload: PayloadDto }`: concrete class that describes the exact real input or output.

Fragments based on the project style (requires local imports for enums and DTOs):

```typescript
@AsyncApiSub({
  channel: WebSocketsComercialChat.JOIN_CHAT,
  summary: 'Join a chat room',
  message: { payload: CreateChatDto },
})
@SubscribeMessage(WebSocketsComercialChat.JOIN_CHAT)
async handleJoinChat(client: CustomSocket, payload: CreateChatDto) {
  // Delegate to the existing application service.
}

@AsyncApiPub({
  channel: WebSocketsComercialChat.JOINED_CHAT,
  summary: 'Joined chat confirmation',
  message: { payload: JoinedChatPayload },
})
private emitJoinedChat(client: CustomSocket, payload: JoinedChatPayload) {
  client.emit(WebSocketsComercialChat.JOINED_CHAT, payload);
}
```

Do not change event directions or names to fit a different interpretation of publish/subscribe. Verify the semantics generated by the installed version. If two namespaces share event names, check that the document does not overwrite or merge them, and document the namespace without renaming the runtime event.

## Payloads And Enums

The [reference DTO class](../assets/asyncapi/create-chat.dto.ts) shows the original format: classes with `@ApiProperty` from `@nestjs/swagger`, descriptions and examples, together with input validators. DTOs live in their transport domain; truly shared contracts go to `core`. Keep optional types, enums, arrays, and nested objects, preserving decorators when moving files.

Use the [enum convention](enums.md) for events and namespaces: domain-local enums or `core/enums/websocket/` when shared. For new errors, preserve EG localization; older DTO examples do not replace that rule.

Check that schemas represent the emitted payload. An array requires an array schema, not a single-item schema. Do not copy old discrepancies between helper type, documented payload, and real value. If a message is encrypted, document the transmitted shape, not only the object before encryption. Socket.IO error shape `{ code, message }` is not the HTTP envelope from the global filter; describe the real WebSocket contract and do not call `switchToHttp()` in a gateway.

## Connection, Authentication, And Flow

Preserve documentation for namespace, Socket.IO path, transport, handshake, and event flow, including join/rejoin, history after reconnect, typing, read confirmations, and private notifications when they exist. Do not document functionality the target does not implement.

The inspected EG chat gateway documents a raw JWT in the `authorization` header, without the `Bearer` prefix. The AsyncAPI setup defines a bearer scheme, but that does not change the real handshake. Document exactly where and in what format the token is sent; do not claim all gateways use Bearer or change authentication while documenting. Also verify the concrete client/transport; do not promise custom headers are available in every browser client.

Socket.IO is not interchangeable with a native WebSocket client. Explain Socket.IO usage and namespace in examples, even when document servers are declared with `ws`/`wss`. Preserve the existing adapter and CORS restrictions; do not copy `origin: '*'` just to add AsyncAPI. Defining a security scheme does not replace guards or JWT verification; also check how it is associated in the generated document when relevant.

## Verification

1. Inspect before/after setup, expected `await` call, registered gateways, enums, payloads, and Swagger link.
2. Generate AsyncAPI locally when the environment allows it and compare channels, directions, messages, schemas, examples, servers, and security. Check resolvable references and verify that decorated private helpers are discovered by the installed version.
3. Open `/sockets-docs` and verify its effective route with the global prefix. Check that the Swagger link reaches that UI.
4. For functional changes, compare at least one incoming event and one outgoing event with their contracts using an isolated local Socket.IO client; do not send real notifications to verify documentation.
5. Run relevant type/build checks. If dependencies or local services are missing, state which generation, UI, or connection check could not run.

Do not remove AsyncAPI when generation fails. Investigate imports, metadata, versions, and schemas, then report the concrete blocker. Do not replace it with HTTP Swagger to hide missing event documentation.
